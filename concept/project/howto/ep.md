# bootsrap a project

This 8-Step Generic Universal Framework can be applied to any project.

| Step | Name | Description | Note |
|----|------|-------------|------|
| 1 | Vision / Goal | Define the name, purpose and objectives of the project or business | <li> Answers "Why?" <li> aligns with Business / Project Objectives |
| 2 | Requirements | Define what is needed in terms of product or service | <li> Answers "What?" <li> aligns with Product / Service Definition |
| 3 | Roadmap / Planned Work | Outline the planned work and timeline | Sets the strategic direction and milestones |
| 4 | Implementation | Execute the build or development process | <li> Answers "How?" <li> actual development / construction phase |
| 5 | Verification & Validation | Test and validate that deliverables meet requirements | Quality assurance; ensure correctness and fitness for purpose |
| 6 | Operations | Run, deploy, and maintain the product or service | <li> Answers "How to run it?" <li> covers ongoing maintenance and support |
| 7 | Measurement & Improvement | Measure performance and iterate for improvement | Continuous improvement; refine and optimize |
| 8 | Feedback Loop | Feed insights back to the beginning | Continuous cycle; loops back to Vision / Goals for ongoing alignment |

```
INPUT ──▶ 1. WHY? ──▶ 2. WHAT? ──▶ 3. WHEN/WHO? ──▶ 4. HOW?
                    │
                    ▼
              5. DOES IT WORK? ──▶ 6. HOW TO RUN? ──▶ 7. HOW WELL?
                    │
                    ▼
              8. WHAT'S NEXT? ──▶ (back to 1)
                    │
                    ▼
                 OUTPUT ──▶ VALUE
```

It supports a several kind of changes

| What changes | What stays the same |
|--------------|---------------------|
| Domain vocabulary | The 8-phase sequence |
| Tools and techniques | The logic: Why → What → When/Who → How → Check → Run → Measure → Adapt |
| Stakeholders | The value-delivery principle |
| Deliverables | The input → output transformation |
| Scale (small to massive) | The framework itself |

# Vision <a id='vision'></a>
The section
- explain why does this project/product/service exists
- must be **very small and durable** to be time proof.
- Example 
  - in software, it should survive major rewrites of the software

```
Vision
├── Name
├── Purpose
├── Problem
├── Desired outcome
└── Principles
```

No:

* programming language
* database
* framework
* current features
* release dates
* architecture
* detailed requirements

Those belong later.

For example, a time-proof vision shouldn't say:

> "Build a Go application using PostgreSQL to provide..."

because the implementation may completely change.

Instead:

> "Provide a shared place where technical knowledge can be created, maintained, discovered, and reused."

That could remain valid for years.

## CMMI vs ITIL

- `ITIL` → distinction between → the service to provide and the technology/processes used to provide it 
- **What are we trying to achieve? → What must be delivered? → How will we implement it?**
- CMMI is heavily focused on **planning, requirements, project management, engineering, measurement, and process improvement**.
- **CMMI's spirit is very much:** don't confuse the **requirements and intended outcomes** with the **engineering solution chosen to achieve them**.
- ITIL is primarily about **managing and delivering services**, rather than managing software development itself.

- ITIL's approach

```
What service/value do we need?
        ↓
What capabilities/processes are needed?
        ↓
How do we design/build/change them?
        ↓
How do we operate the service?
        ↓
How do we improve it?
```

For example:

| Level              | Your `rctl` project                         | Documentation platform                      |
| ------------------ | ------------------------------------------- | ------------------------------------------- |
| **Vision**         | Make resource management easy from terminal | Make organizational knowledge easy to share |
| **Product**        | CLI commands, UX, capabilities              | Documents, collaboration, search            |
| **Implementation** | Go/Rust, CLI framework, API client          | React, database, API, auth                  |
| **Operations**     | Releases, packaging, support                | Deployment, monitoring, backups             |

And **roadmap belongs primarily at levels 1–2**.

Technical plans, architecture decisions, and implementation tasks belong primarily at **level 3**.

Operational plans belong at **level 4**.

### This also solves an important problem

Suppose you write:

> "We need PostgreSQL."

That's an **implementation decision**.

But the actual requirement might be:

> "The platform must persist documents reliably and support concurrent access."

Those are very different statements.

You want your project documentation to preserve that distinction:

```text
REQUIREMENT
"Documents must be reliably persisted."
"Documents must be versioned."

        ↓

DESIGN CONSTRAINTS
- durable storage
- transactional updates
- concurrent access

        ↓

OPTIONS
- PostgreSQL
- MySQL
- another database

        ↓

DECISION
PostgreSQL

        ↓

IMPLEMENTATION
PostgreSQL schema + migrations + backup strategy
```

That separation is extremely valuable because **your implementation can change without invalidating the project requirement**.

So, if your goal is to build a reusable way of organizing projects like `rctl` and your shared documentation platform, I'd recommend thinking in terms of:

**Vision → Requirements → Roadmap → Architecture/Design → Implementation → Operations → Improvement**

That's much closer to the mindset behind frameworks such as CMMI and ITIL than simply having "a project roadmap and a technical roadmap."
